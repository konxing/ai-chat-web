# 向量检索 go / no-go（认知层，只出结论的一片）

这片**不写实现**。它只回答一个问题：剩下那批关键词召回捞不回来的标准答案，值不值得为它上向量。
交付物是这份取舍 + 成本 + 一个结论，以及「以后什么条件下要重新算这笔账」。

结论先放这儿：**no-go**。理由是三句话，细节在下面各节：

1. 缺口是相关性盲区没错（44 条全部与查询零共同词），但**其中 11 条用一个更便宜、且不改接口形状的改法就能捞回来**——
   代价是它会打破 `update` 守卫（实测，见第三节）。
2. 打破守卫这件事**不是词法特有的毛病**：被禁止端出去的那条，和正确那条讲的是同一件事、同一个故事，
   语义相似度只会把它们贴得更近，不会更远。向量在这批残余上的真实收益上限因此比「33 条」还要低，
   而**这个判断本机无法实测**——没有 pgvector、没有 embedding 端点、没有任何向量代码。
3. 落地前置动作（装扩展 / 改镜像 / 加第二个 provider 端点 / 每轮提问多一次串行往返 / 「向量算不算明文记忆」这条红线未定）
   每一个都不在「优化」范围内，属于**上线前新增基础设施**。在真库里今天连一行记忆都没有的时候做这件事，是给 0 个用户预付一笔不可逆的成本。

下面每一节都标了是**实测**还是**推断**。

## 二、44 条到底是什么性质的缺口（实测）

分类脚本一次性跑完，四条判据互斥且穷尽。做法是**先复刻 `selectMemoryCandidates` 的第一半**
（`memory-module.ts:104-108` 的 `rows.filter(isMemoryUsable)`，**不截断**），再对每条漏掉的 gold 看：
它在不在过滤后的池子里、它和查询有没有共同 token、它排在第几。

> 这里踩过一个坑值得记下来：第一版直接拿 `selectMemoryCandidates` 的返回值分类，
> 那个函数已经截到 8 条了，于是 44 条**全被判成「不在池子」**——一个漂亮的假结论。
> 判断依据必须是先不截断的池子（166/168 行），再看 rank。

| 分类 | 条数 |
|---|---|
| 不在候选池（被保留期 / 时效 / 会话隔离挡掉——**任何检索都治不了**） | **0** |
| 与查询**零共同 token**（词法召回的原理性盲区） | **44** |
| 有共同 token，但被无关噪声挤出名额 | 0 |
| 有共同 token，但被同故事近邻挤出名额 | 0 |

**44/44 全在第二栏**，一条不落。它们的 rank 从 16 一直到 158（池子 166 或 168 行）。

这意味着两件相反的事，都必须说清：

- **好消息**：缺口不是名额问题也不是池子问题。池子已经足够大、`isMemoryUsable` 没有误杀、
  8 个名额没有浪费在挤掉正确答案的噪声上。把 `MEMORY_RETRIEVAL_POOL`（`memory-module.ts:52`，现在 200）
  调大、或者把 `MEMORY_READ_MAX_ITEMS`（`:41`，现在 8）调大，**一条都救不回来**。
- **坏消息**：缺口 100% 落在「字面不重合」这一类，而这正是关键词召回的原理边界。
  一个完美排序器在这一批上的天花板是 Recall@8 = 1.0。所以靶子是真的，不是虚的。

几条典型（问 → 该召回的原话）：

- 「我现在向谁汇报」→「行政上跟产品总监」
- 「我雅思哪一项最弱」→「写作一直是我的短板」
- 「我还钓鱼吗」→「我不钓了，装备挂在闲鱼了」
- 「为什么不当面试官了」→「HC 冻结了」

## 三、先试便宜的：同一批探针，三个打分器（实测）

**上向量之前，先测不要向量的改法。** 三个臂跑的是同一份 fixture、同一套 `scoreProbe` / `summarizeArm`
（直接复用 `scripts/cognitive-eval/metrics.ts`，不另写指标——第一版自己手搓宏平均时 gold 为空会除零变 NaN，
而且和官方口径对不上；改成复用官方函数后，`现状` 臂的数字和 `summary.json` **逐项完全吻合**，复刻成立）。

| 打分器 | Recall@8 | MRR | 至少命中一条 | 违禁注入 | 残余未召回 |
|---|---|---|---|---|---|
| `bigram`（现状，`retrieval.ts` 现在这个） | 0.7274 | 0.5828 | 80.4% | **0** | 44 |
| `bigram + unigram`（中文再补单字 token） | 0.7835 | 0.6203 | 86.0% | **1** | 36 |
| `整串字符集合`（整句字符当集合匹配） | **0.7975** | **0.6444** | 86.9% | **1** | **33** |

`现状` 那一行的分类通过：update 17/30、conflict 13/13、recall 41/60、temporal 7/7、forgetting 6/6。
最松那一行：update **19/30**、conflict 13/13、recall 47/60、temporal 7/7、forgetting 6/6。

### 收益是真的，而且不小

只改 token 切分，**不动接口、不动数据库、不加依赖**，Recall@8 从 0.7274 到 0.7975（+0.070），
残余从 44 降到 33。这一节把「向量的靶子」从 44 条压到了 **33 条**。

### 代价是一条违禁注入，而且它打在最重要的守卫上

两个松匹配臂的违禁都来自同一个探针：

> `s14-p1`（类别 `update`）：查询「我转组的事定了吗」，gold 是 `s14-m6`「我决定转去中台组」，
> forbidden 是 `s14-m3`「我先不转，把手上的网关收尾」和 `s14-m1`「我在想要不要转到中台组」。
> 松匹配把 `s14-m1` 抬进了前 8。

`s14-m1` 是 50 天前那次**最初的犹豫**（fixture `stories-batch1.ts` 里它的 note 还专门写了
为什么它被归到 `personalGoal`）。把它端出去，就是**把已被后续说法取代的旧想法当成现行结论**——
任务书里 `update` 这一类存在的唯一理由就是防这个。现状臂违禁 0，是这条守卫真的在起作用；
一旦为召回率放松匹配，它立刻破。

### 由此推出对向量的关键判断（**推断，本机无法实测**）

这条推断要写清楚，因为它是 no-go 的承重墙：

`s14-m1`「我在想要不要转到中台组」和 `s14-m6`「我决定转去中台组」——
同一个故事、同一个话题、几乎同一组词，**在语义向量空间里它们的距离会比在词法空间里更近，不是更远**。
稠密向量擅长的是「这两句在说同一件事」，而 `update` 守卫要的是「哪一句是现在算数的」。
后者不是语义相似度问题，是时间有效性问题——那个信息在 `supersededAt` / `validFrom` 这些列上
（`schema.prisma:457-459` 的 `supersededAt` / `validFrom` / `validTo`），**不在向量里**。

所以：把匹配放松（无论靠词法还是靠语义）都会撞开 `update` 守卫；向量捞回残余 33 条的同时，
大概率会在别的探针上制造同类违禁。**向量不是这条盲区的解药，它只是把同一个病换一种方式放大。**

这个判断**没有被实测支持过**——本机没有 embedding，跑不出向量臂。它只能算读着 fixture 想出来的推理。
真要上向量，这一条必须先变成可测的断言。

## 四、残余 33 条里，向量也未必接得住的（实测取样 + 推断）

33 条里有几条明确不是「换个相似度度量」能解决的：

- `s27-p4`「为什么不当面试官了」→「HC 冻结了」：这是**跨句的因果推理**，两句之间没有任何词汇或主题重合，
  靠的是「HC 冻结 ⇒ 没有面试可做 ⇒ 不当面试官」这一步常识。
- `s25-p2`「我为什么考虑换车」→ `s25-m2`「修一次要三千多」＋ `s25-m1`「我在想要不要把那辆老车换了」：
  一条 gold 是**理由**，一条是**结论**，查询要的是把两者连起来。

稠密向量在短汉语句子上对这类关系的召回，公开评测里也不是稳赢的。**这两条是「向量的期望收益低于 33 条上界」的具体来源**，
属于推断，不是本机观测。

## 五、本机代价实测（数字是真的，但**只覆盖成本的一部分**）

一次性基准脚本（跑完就删，输出全贴在这儿）。形状按线上真实读侧取：
池子 `MEMORY_RETRIEVAL_POOL = 200` 行，1024 维 float32，密文列和 `contentCiphertext` 一样是 TEXT，
加解密走真 `src/lib/crypto.ts`（AAD 每行不同，和 `memories.ts:180` 的 `aadFor` 同构）。

### 存储与读取

```
维度 1024，池子 200 行
单条向量：明文 4,096 B → 密文 7,336 字符（base64）
整池密文合计 1.40 MB（每次读记忆都要过的量）
```

同一个 200 行临时表上，三种读取各跑 3 轮（毫秒，到端 MB）：

| 读取形状 | 轮 1 | 轮 2 | 轮 3 | 到端 |
|---|---|---|---|---|
| 只取 id + 时间 | 1.7 | 1.0 | 1.1 | ~0 MB |
| 带正文密文（**现状的形状**） | 9.0 | 8.6 | 7.9 | 1.40 MB |
| 带正文密文 **+ 向量密文** | 14.7 | 14.0 | 14.2 | 2.80 MB |

**读侧多 5–6 ms、多 1.40 MB**（每轮对话都要付一次）。

### 应用层暴力检索

pgvector 本机没有（第六节），所以唯一可行形状是「整池捞回 → 解密 → 应用层余弦」：

```
应用层整池「解密 + 余弦 + 排序」：中位数 3.51 ms，最慢 4.81 ms
```

（前 5 次跑丢弃，那是要付 V8 JIT 和 AES-GCM 初始化的钱；之后取 31 次中位数。）

### 这一节没覆盖什么（必须写清，否则上面的数字会被当成「向量不贵」）

- **不含查询向量的 embedding 调用**。每轮提问要先调一次 provider 拿查询向量，那是**一次串行的、挡在回答前面的网络往返**。
  本机没有可打的端点，**RTT 未实测**，一次都没测过。今天这轮对话的延迟预算里根本没有这一跳。
- 不含写侧：每条新记忆要 embed 一次。这个可以塞进已有的后台队列（`CognitiveTask`），不算阻塞——
  但它是**新依赖**，不是新逻辑。
- 不含内存：整池密文 + 明文向量同时驻留在一次请求里。
- 临时表在事务里、和真表不同的缓存状态；**它的绝对值不能当线上承诺**，只有三列之间的差值可信。

## 六、落地前提核查（全部实测，含可复现命令）

这一节回答「真要上，今天挡在前面的是什么」。四条，每条都是能跑的：

### 1. 本机 PostgreSQL 没有 pgvector

```
pg_available_extensions 总行数 61
  pg_trgm 默认 1.6  已装 否
服务器：PostgreSQL 17.11 on x86_64-windows
```

61 个可用扩展里**没有 `vector`**。连 `pg_trgm` 都只是可用、没装。
⇒ 任何「装 pgvector」的动作都等于**改数据库发行版**：本机是 Windows 上的自建实例（数据在 `D:\FamilyAIChat`），
线上是还没定的部署形态。**这是基础设施变更，不是代码变更。**

顺带一句：密文列上 SQL 侧的文本检索（`pg_trgm` 之类）**原理上不成立**——库里存的是密文，
三元组打出来的重合度是噪声。任务书 5.3 认的就是「匹配只能在应用层解密之后做」这条路，
`retrieval.ts:7-8` 的注释写了这件事。

### 2. Prisma 6.11.1 对 `vector` 的三条实证

用一份一次性 schema 跑 `prisma validate` / `generate` / `migrate diff`（不碰真 schema、不连真库）：

| 试什么 | 结果 |
|---|---|
| `emb Vector?` 这个原生类型 | **不认**：`Type "Vector" is neither a built-in type...`。Prisma 6.11 没有 Vector 类型。 |
| datasource 里写 `extensions = [vector]` | **报错**：`The extensions property is only available with the postgresqlExtensions preview feature.` ⇒ 还**是 preview**，没 GA。 |
| `previewFeatures = ["postgresqlExtensions"]` + `extensions = [vector]` + `emb Unsupported("vector")?` | **schema 有效**。 |
| 对这份 schema `migrate diff --from-empty --script` | 生成的 DDL 第一句是 **`CREATE EXTENSION IF NOT EXISTS "vector";`** ⇒ 迁移一旦 apply，**在没有这个扩展的机器上直接失败**（本机就是这台机器）。 |
| `generate` 出来的 client 里有没有 `emb` 这个字段 | **完全没有**：`index.d.ts` 里只有 `id` 和 `embCrypt`，`Unsupported` 列对 Prisma Client **不可见**。 |

最后一条是本片最要紧的落地事实，它决定接口形状：

> 今天读记忆是 `prisma.memoryItem.findMany({ where: ... , take: 200 })`，一个调用同时做
> 「按 userId + 时效过滤」和「取回正文」。列一旦是 `Unsupported`，`findMany` **看不见它**，
> 要拿向量只有两条路：
> ① 整条查询改写成 `$queryRawUnsafe`——那 `isMemoryUsable` 前面那段过滤条件的 SQL 版本就得由手写维护（等于把保留期/时效规则的第二个实现搬出 mock 边界，而这块今天**全部止于内存替身**，见 `cognitive-acceptance.md`）；
> ② 两段式：`findMany` 拿 id，再裸 SQL 按 id 取向量——多一次往返，且顺序/名额要在两边保持一致。
>
> 无论哪条，都**不是加一列**，是**换一条读路径的接口**。
> KNN 排序（`<=>` 运算符 + HNSW 索引）更是只能走裸 SQL；而密文向量**不能被 HNSW/IVFFlat 索引**
> （索引用的是原向量距离，密文没有这个几何结构），所以即便装了扩展，本项目的加密形状也用不上它的索引能力。

### 3. 本机没有任何 embedding 能力，src 里也没有向量代码

```
ollama 命令行：不存在
package.json 里推理/向量相关依赖：无
src/ 里 "embedding" 的命中：只有两处注释，零代码
```

那两处注释自己就记着这件事：

`src/lib/cognitive/retrieval.ts:15-16`「向量、图扩展、Reranker、RRF 都不在这里：向量要独立的 Embedding Provider 配置」。

出站侧只有**一个端点**：`src/lib/ai.ts:123` 的 `joinApiPath(provider.baseUrl, '/chat/completions')`。
⇒ 上向量要在 provider 体系里开**第二个端点（`/embeddings`）、第二条 Key 路径、第二条出站代码路径**，
同时带来限流、体积上限、审计、错误处理这套东西各一份。用户长期指令里「防攻击要做好」这一条，
在这里是**新增攻击面**，不是优化。

## 七、「向量算不算明文记忆」——这条红线没定（未决）

任务书红线：日志、审计、新建表里**不得出现明文记忆、明文历史消息、私人情绪内容、明文反思**。

一条 1024 维 float32 向量是不是「明文记忆」？诚实的回答是**不知道**：

- 它不是可读文本，按字面读不算明文；
- 但embedding 对短句是**可近似反演**的——拿一个候选句子集合，把候选各自 embed、和存储向量比距离，
  能选出近似原句。这个可逆性**本机没有证过，也没有证否**（没有 embedding 就跑不了这个实验）。

所以两种走法各有代价，且**这一条决定第六节那条接口选择**：

| 判定 | 后果 |
|---|---|
| 算明文 → 必须加密 | 密文不能被 HNSW/IVFFlat 索引 ⇒ pgvector 白装 ⇒ 只剩「整池解密 + 应用层余弦」（第五节测的就是这条路：读侧 +5–6 ms、+1.40 MB，每轮都付）。 |
| 不算明文 → 存原向量 | 检索能进数据库、能建索引、延迟最好；但**在没有证明不可反演之前，这是往新列里写明文记忆**。按本仓库一贯的口径（正文、反思、理由全都加密，AAD 绑 userId + 行 id），这一格不该由性能来判。 |

**这片不替用户拍这一条**。它是产品/隐私判断，不是技术判断；而且它没有实测可依据。

## 八、结论：no-go，以及什么条件下要重新算这笔账

### 为什么是 no-go（把三条理由按承重排序）

1. **收益的上界是 33 条，而它的地基是推断。** 44 条缺口里 11 条已被更便宜的词法改法覆盖（实测），
   剩下 33 条里至少有 2 条明确需要跨句推理（第四节）。向量能捞回其中几条，本机一个都没测过。
   在「没测过」的前提上装扩展、改镜像、开第二个 provider 端点、换读路径接口——这笔交换的双方不对等。
2. **它会撞开最要紧的那条守卫，而且撞的方式和词法一样。** `s14-p1 → s14-m1` 是实测的：放松匹配 ⇒
   旧的犹豫被当现行结论端出去 ⇒ `update` 类别的通过数从 17/30 变成 19/30 的同时，违禁从 0 变成 1。
   语义相似度只会把「同一件事的两个版本」贴得更近。守卫要的信息在时间列上，不在向量里。
3. **前置动作全在「上线前新增基础设施」那一栏。** 装/改数据库发行版、Prisma 侧要么裸 SQL 要么两段式
